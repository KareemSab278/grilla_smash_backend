# Ordering System Backend

A generic online-ordering API (menu, branches, offers, orders) written in strict TypeScript on Express 5, storing everything in Postgres on Supabase. It is the single backend for the customer storefront, the admin panel and (later) the KDS.

## 1. Overview

| | |
|---|---|
| Runtime | Node.js 24+ |
| Language | TypeScript, `strict` plus `noUncheckedIndexedAccess`, `noUnusedLocals`, `noImplicitReturns` |
| HTTP | Express 5 + `cors` |
| Validation | [zod](https://zod.dev) (request bodies and queries) |
| Database | Postgres (Supabase) through the [`postgres`](https://github.com/porsager/postgres) driver |
| Tests | Node's built-in test runner via `tsx`, plus an end to end `curl-tests.sh` |

Design goals: every layer has one job, all SQL lives in one file, nothing is `any`, and a request can never half-succeed (multi step writes run in a transaction).

Money is always an **integer in pence** (`£8.99` is `899`). Ids are 12 character hex strings generated by the backend.

## 2. Quick start

### 2.1 Prerequisites

- Node.js 24 or newer
- A Supabase project (or any Postgres you can reach over TLS)

### 2.2 Create the tables

1. Open Supabase, go to **SQL Editor**.
2. Paste the whole of [`schema.txt`](./schema.txt) and run it. It is safe to run again, everything is `IF NOT EXISTS` / `OR REPLACE`.
3. If you already have an older deployment, also run [`migrations/20261011_branch_hours_and_availability.sql`](./migrations/20261011_branch_hours_and_availability.sql) to add the new branch columns in place.
4. Also run [`migrations/20261013_user_email_and_business_key.sql`](./migrations/20261013_user_email_and_business_key.sql) (adds `users.email` and `business.key_hash`). Then set the business key once, see [8.14](#814-users-and-password-reset).

### 2.3 Configure

Create `Backend/.env` (see [section 3](#3-environment-variables) for every option):

```env
PORT=8000
HOST=127.0.0.1
SUPABASE_DB_URL=postgresql://postgres.<project-ref>:<db-password>@aws-0-<region>.pooler.supabase.com:5432/postgres
DB_POOL_MAX=10
REDIS_URL=redis://127.0.0.1:6379
CORS_ORIGINS=*
BRANCH_SETTINGS_AUTH_ENABLED=false
STRIPE_SECRET_TEST_KEY=sk_test_...
RESEND_API_KEY=re_...
```

Take the connection string from **Supabase > Project Settings > Database > Connection string** (use *Session pooler*). If it does not connect, see [Troubleshooting](#13-troubleshooting).

### 2.4 Run

```bash
npm install
npm run dev          # watch mode, http://127.0.0.1:8000
```

Check it:

```bash
curl http://127.0.0.1:8000/health        # {"status":"ok"} once the database is reachable
```

Run the full endpoint smoke test: `./curl-tests.sh` (see [Testing](#9-testing)).

### 2.5 Production

```bash
npm run build        # compiles src/ to dist/
npm start            # node dist/server.js
```

## 3. Environment variables

Read once at startup by [`src/config.ts`](./src/config.ts). A missing or invalid value throws immediately, the server never starts half configured. `.env` is loaded from the directory you start the process in.

| Variable | Required | Default | Description |
|---|---|---|---|
| `SUPABASE_DB_URL` | yes (or `DATABASE_URL`) | none | Postgres connection string. Takes priority over `DATABASE_URL`. |
| `DATABASE_URL` | yes (or `SUPABASE_DB_URL`) | none | Fallback name for the same thing. |
| `REDIS_URL` | yes | none | Redis connection string used for rate limiting. The server fails startup if Redis is unavailable. |
| `PORT` | no | `8000` | Integer 0 to 65535. |
| `HOST` | no | `127.0.0.1` | Interface to bind. Use `0.0.0.0` in a container. |
| `DB_POOL_MAX` | no | `10` | Max pooled connections, integer 1 to 100. |
| `CORS_ORIGINS` | no | `127.0.0.1` / `localhost` on ports 3000 and 3001 | Comma separated list of allowed browser origins, or `*` to allow any browser origin in dev. |
| `BRANCH_SETTINGS_AUTH_ENABLED` | no | `false` | Turn branch-setting auth on when you have users/roles wired in. Leave it off for local development. |
| `STRIPE_SECRET_TEST_KEY` | yes | none | Stripe secret key used by the `/payments/stripe/*` routes. |
| `SHIFT4_SECRET_KEY` | no | none | Shift4 secret key (fallback provider). Without it the Shift4 routes answer 503. |
| `RESEND_API_KEY` | yes | none | Resend API key, used for order status emails and password reset codes. |
| `EMAIL_FROM` | no | `test_business <grillasmash@gmail.com>` | Sender of every email. This is a testing sender for the current Resend setup; override it with your verified business address in production. |

`SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` and `SUPABASE_JWKS_URL` may be present in `.env` but **the backend does not use them yet**. They are for Supabase Auth, which is not wired in (see [section 12](#12-known-limitations-and-roadmap)). `@supabase/server` is installed for that purpose.

`.env` is git-ignored. Never commit it, it contains secrets.

## 6. How it works

### 6.1 Request lifecycle

```
request
  -> cors -> express.json (1 MB limit)
  -> router (src/requestHandlers/*)
       -> parseInput(zodSchema, body)          422 if invalid
       -> dbGet / dbAll / dbRun / transaction  static SQL from queries.ts
       -> res.json(...)
  -> notFoundHandler                           404 for unknown routes
  -> errorHandler                              any thrown error becomes { "detail": "..." }
```

Handlers are `async` and simply `throw` (`notFound(...)`, `badRequest(...)`). Express 5 forwards rejected promises to the error handler, so there are no `try/catch` blocks in handlers.

### 6.2 Conventions worth knowing

- **All SQL is static** and lives in `queries.ts`, grouped as `QUERIES.GET / POST / PUT / PATCH / DELETE`. Values are always bound as `$1, $2...`, so SQL injection is not possible. Never build SQL from input.
- **Updates are partial.** `UPDATE` queries use `COALESCE($n, column)`: send only what you want to change. `null` or omitted both mean "leave unchanged" (see the limitation in [section 12](#12-known-limitations-and-roadmap)).
- **No N+1 queries.** Lists load child rows in one query (`WHERE parent_id = ANY(...)` or an optional-parent pattern) and stitch them together in memory with `groupBy`.
- **Transactions.** Anything that writes more than one row runs inside `transaction(async tx => ...)`. Use the `tx` handle, never the pool, inside it. Throwing rolls everything back.
- **Missing rows become 404 for free.** `UPDATE ... RETURNING` and `DELETE ... RETURNING id` return no row when the id does not exist, `requireRow` turns that into a 404.
- **`updated_at`** is maintained by a database trigger, handlers never set it.
- **Typed boundary.** The driver returns untyped rows, `dbAll<T>` / `dbGet<T>` are the one place a row type is asserted. Everything above them is fully typed.

### 6.3 Errors

Every error is `{ "detail": "<message>" }` (the shape the Admin and Frontend already read).

| Status | When | Source |
|---|---|---|
| 400 | Business rule broken (e.g. `min_selections` above `max_selections`, unavailable product on an order), malformed JSON | `badRequest()` |
| 404 | Row or route does not exist | `notFound()` |
| 409 | Duplicate value, or deleting something still referenced (e.g. a branch with orders) | `conflict()` / database error mapping |
| 422 | Request body or query failed validation. The message lists each bad field | `parseInput()` |
| 500 | Anything unexpected. Logged server side, the client only sees `Internal server error` | `errorHandler` |

Database constraint errors are mapped in [`db.ts`](./src/db.ts): unique violation to 409, foreign key violation to 409, check / not null / bad data to 400.

### 6.4 Startup and shutdown

`server.ts` binds `HOST:PORT`. On `SIGINT` / `SIGTERM` it stops accepting requests, lets in-flight ones finish, closes the connection pool and exits (forced exit after 10 seconds so a stuck connection cannot hang a deploy).

## 7. Database

Defined in [`schema.txt`](./schema.txt). 20 tables:

| Group | Tables |
|---|---|
| Company | `business` (single row), `branches` |
| Menu | `categories`, `products`, `product_categories` |
| Modifiers | `modifier_groups`, `modifiers`, `product_modifier_groups` |
| Branch pricing | `branch_product_overrides` |
| Offers | `offers`, `offer_rules`, `offer_rule_products`, `offer_rule_modifier_groups`, `offer_rule_modifiers` |
| Orders | `orders`, `order_items`, `order_item_modifiers`, `order_offers`, `payments` |
| Admin | `users` (created and password-reset through `/user/*`, see [8.14](#814-users-and-password-reset)) |

### 7.1 Relationships

```
business (1 row)

branches ──< orders ──< order_items ──< order_item_modifiers
   │            ├──< order_offers
   │            └──< payments
   └──< branch_product_overrides >── products

categories >──< products >──< modifier_groups ──< modifiers
          (product_categories)  (product_modifier_groups)

offers ──< offer_rules >──< products
                │
                └──< offer_rule_modifier_groups ──< offer_rule_modifiers
```

### 7.2 Things the schema guarantees

- Booleans are real `BOOLEAN`, timestamps are `TIMESTAMPTZ`, money is `INTEGER` pence with `CHECK >= 0`.
- Only one `business` row can exist (unique index on a constant).
- `min_selections <= max_selections` and `required` implies `min_selections >= 1` are `CHECK` constraints.
- Deleting a product / modifier / offer **never** damages old orders: order rows copy the name and price (snapshots) and their foreign keys use `ON DELETE SET NULL`. A branch with orders cannot be deleted.
- Foreign keys are indexed (Postgres does not do it automatically).
- `updated_at` triggers keep timestamps correct even for edits made in the Supabase dashboard.

### 7.3 Row level security

RLS is **enabled on every table with no policies**. Supabase exposes every public table over its REST API using the public anon key, this locks that door completely. The backend connects with the direct Postgres login, which bypasses RLS, so it is unaffected. Do not add permissive policies unless you intend to expose a table to browsers.

## 8. API reference

Base URL: `http://127.0.0.1:8000` (no prefix). All bodies are JSON, send `Content-Type: application/json`.

### 8.1 Conventions

- Ids are 12 character hex strings. `:id` in a path means one of those.
- Money is integer pence.
- Timestamps are ISO 8601 strings (`2026-10-08T11:45:44.174Z`). Request dates accept anything `Date` can parse, such as `2026-01-31T18:30` from a `datetime-local` input.
- Successful creates and updates return the full row (200). `POST /orders` returns 201.
- Deletes return `{ "success": true, "deleted": "<id>" }`.
- Unknown body fields are ignored.
- "Partial update" means only send what you want to change.
- Most routes are still public, but branch-setting writes now require an active `ADMIN` or `MANAGER` user; see [Security notes](#11-security-notes).

Error example:

```json
{ "detail": "'Burger' needs at least 1 from 'Sauce'" }
```

### 8.2 Health

| Method | Path | Description |
|---|---|---|
| GET | `/` | `{ "name", "version", "status": "running" }` |
| GET | `/health` | `{ "status": "ok" }`. Queries the database, so it returns 500 when the database is down |

### 8.3 Business

One business per deployment.

| Method | Path | Description |
|---|---|---|
| GET | `/business` | The business, or `null` if not created |
| POST | `/business` | Create it. 400 `Business already exists` if there is one |
| PUT | `/business/:businessId` | Partial update |

Body fields: `name`\*, `slug`\*, `logo_url`, `currency` (default `GBP`). Update also takes `active` (boolean).

`POST /business` also generates the **business key** and returns it once as `business_key`. Only its sha256 hash is stored (`business.key_hash`), it is never returned again and `GET /business` never includes it. Save it, the admin panel needs it for the `/user` routes.

```bash
curl -X POST localhost:8000/business -H 'Content-Type: application/json' \
  -d '{"name":"Grill'"'"'a Smash","slug":"grilla-smash"}'
```

### 8.4 Branches

| Method | Path | Description |
|---|---|---|
| GET | `/branches` | All branches ordered by name |
| GET | `/branches/:branchId` | One branch |
| POST | `/branches` | Create |
| PUT | `/branches/:branchId` | Partial update |
| PATCH | `/branches/:branchId/opening-hours` | Partial weekly schedule update |
| PUT | `/branches/:branchId/unavailable-products/:productId` | Mark a product unavailable at one branch |
| DELETE | `/branches/:branchId/unavailable-products/:productId` | Restore product availability at one branch |
| DELETE | `/branches/:branchId` | Delete. 409 if the branch has orders |

Body fields: `name`\*, `address_line1`\*, `city`\*, `postcode`\*, `address_line2`, `phone`, `latitude` (-90 to 90), `longitude` (-180 to 180). Create also accepts `opening_hours`; omit it to use the default 09:00-17:00 schedule for every day. Update also takes `active`.

`opening_hours` is stored as JSON and returned on every branch response:

```json
{
  "monday": { "open": "09:00", "close": "17:00", "is_closed": false },
  "tuesday": { "open": "09:00", "close": "17:00", "is_closed": false },
  "wednesday": { "open": "09:00", "close": "17:00", "is_closed": false },
  "thursday": { "open": "09:00", "close": "17:00", "is_closed": false },
  "friday": { "open": "09:00", "close": "17:00", "is_closed": false },
  "saturday": { "open": "09:00", "close": "17:00", "is_closed": false },
  "sunday": { "open": "09:00", "close": "17:00", "is_closed": false }
}
```

PATCH `/branches/:branchId/opening-hours` accepts only the days you want to change. For example, sending only `monday` updates Monday and leaves the other six days unchanged. A closed day can be represented with `{ "is_closed": true }`.

### 8.7 Modifier groups

| Method | Path | Description |
|---|---|---|
| GET | `/modifier-groups` | All groups with modifiers |
| GET | `/modifier-groups/:groupId` | One group |

### 8.10 Branch hours and availability

The branch row now includes both `opening_hours` and `unavailable_products`. `unavailable_products` is a simple `text[]` list of product ids that are hidden from that branch's customer menu and rejected again when an order is created.

### 8.11 Branch product overrides

Lets a branch hide a product or charge a different price. `null` means "use the normal value".

| Method | Path | Description |
|---|---|---|
| GET | `/branches/:branchId/products` | Active products available at the branch, each with `branch_active`, `price_override` and `effective_price` |
| PUT | `/branches/:branchId/products/:productId` | Set the override (it is replaced as a whole) |
| DELETE | `/branches/:branchId/products/:productId` | Remove the override |

PUT body: `{ "active": false }` and/or `{ "price_override": 799 }`. A product with `active: false` is hidden from that branch and cannot be ordered there.

Branch availability now also honours `branches.unavailable_products`:

- `GET /branches/:branchId/products` filters those ids out of the customer menu.
- `POST /orders` rejects them again, even if someone submits the ids directly.
- Managers can toggle them with the branch routes above.

### 8.12 Offers

An offer is a configurable bundle or discount. It has **rules** (slots such as "Main", "Side", "Drink"), each rule lists allowed products and optionally modifier groups with their own min / max.

| Method | Path | Description |
|---|---|---|
| GET | `/offers` | All offers with nested rules |
| GET | `/offers/:offerId` | One offer |
| POST | `/offers` | Create offer and rules in one transaction |
| PUT | `/offers/:offerId` | Partial update. `rules` (when sent) **replaces** every rule |
| DELETE | `/offers/:offerId` | Delete |

Offer fields: `name`\*, `description`, `type` (`FIXED_PRICE` default, `PERCENTAGE`, `FIXED_DISCOUNT`, `BUY_X_GET_Y`), `price` (pence), `percentage` (0 to 100), `discount_amount` (pence), `starts_at`, `ends_at`, `sort_order`, `active` (default true), `rules`.

Rule fields: `name`\*, `quantity` (default 1), `sort_order`, `product_ids`, `modifier_groups`.
Rule modifier group fields: `modifier_group_id`\*, `required`, `min_selections`, `max_selections`, `modifier_ids` (restrict the group to these modifiers).

Validated before anything is written, otherwise 400 / 404: products, groups and modifiers must exist, a modifier must belong to the group it is listed under, a group cannot be listed twice in one rule, `min <= max`, and `required` needs `min >= 1`.

```json
{
  "name": "Burger Meal", "type": "FIXED_PRICE", "price": 1199,
  "rules": [
    { "name": "Main", "product_ids": ["<productId>"],
      "modifier_groups": [ { "modifier_group_id": "<groupId>", "required": true,
                             "min_selections": 1, "max_selections": 2, "modifier_ids": ["<modifierId>"] } ] },
    { "name": "Drink", "product_ids": ["<productId>"] }
  ]
}
```

> Offers are applied when an order is created, see [Ordering an offer](#ordering-an-offer). A rule modifier group with no `modifier_ids` lists every active modifier of the group in responses.

### 8.13 Orders

| Method | Path | Description |
|---|---|---|
| POST | `/orders` | Create an order (201) |
| GET | `/orders/:branchId` | Active orders for a branch: `PENDING`, `ACCEPTED`, `PREPARING`, `READY`. Newest first |
| GET | `/orders/history/:branchId` | **Every order from the last 30 days**, any status, newest first |
| PATCH | `/orders/status` | Change an order's status |

Both GET routes return `{ "orders": [ ... ] }`, each order with its `items`, each item with its `modifiers`. They 404 for an unknown branch.

#### Create an order

The client sends **only ids and customer details**. It never sends prices or totals: the server prices the order from the database, so a tampered request cannot change what is charged (any `price` / `total` sent is ignored).

Body fields:

| Field | Required | Notes |
|---|---|---|
| `branch_id` | yes | Must exist |
| `order_type` | no | `PICKUP` (default) or `DELIVERY` |
| `customer_name` | yes | |
| `customer_phone`, `customer_email` | no | Email must be valid |
| `address_line1`, `address_line2`, `city`, `postcode` | for `DELIVERY` | `address_line1`, `city` and `postcode` are required when delivering |
| `delivery_fee` | no | Pence, default 0. Only counted for `DELIVERY` |
| `notes` | no | Up to 2000 characters |
| `items` | one of `items` / `offers` | Up to 100 items |
| `items[].product_id` | yes | |
| `items[].quantity` | yes | 1 to 99 |

| `payment` | no | `{ "provider": "stripe", "payment_reference": "pi_123" }` (or the legacy `provider_payment_id`), recorded in `payments` as `PENDING` |


#### How an order is priced and checked

For each item, in this order:

1. The product must exist (404), be `active`, and not be switched off for that branch (400).
2. Unit price = the branch's `price_override` if set, otherwise the product `price`, **plus** the price of each selected modifier.
3. Every selected modifier must be active and belong to a group attached to *that* product (400 otherwise). Selecting the same modifier twice is rejected.
4. For each attached group: the number selected must be at least `min_selections` (at least 1 if `required` and the group has available choices) and at most `max_selections` (400 otherwise).
5. Line total = unit price x quantity.

Then `subtotal` = sum of line totals, `total` = `subtotal` + `delivery_fee` (delivery only), `discount` is 0.

Worked example from the tests above: a £8.99 burger with Mayo (+50p) and BBQ (+25p), quantity 2, plus a £3.00 side: `2 x (899 + 50 + 25) + 300 = 2248`.

#### Order numbers

`order_number` is a counter **per branch** starting at 1. It is allocated inside the create transaction under a Postgres advisory lock per branch, so simultaneous orders on one branch can never receive the same number (tested with 12 parallel requests).

#### Statuses

`PENDING` (initial) → `ACCEPTED` → `PREPARING` → `READY` → `COMPLETED`, or `CANCELLED`. Any status can be set to any other, there are no transition rules yet.

If the order has a `customer_email`, the customer is emailed on creation (`PENDING`) and on every status change (see `src/orderEmails.ts`). Email is fire and forget: a failed send is logged and never fails the request.

```bash
curl -X PATCH localhost:8000/orders/status -H 'Content-Type: application/json' \
  -d '{"id":"c7cea41be001","status":"PREPARING"}'
# {"id":"c7cea41be001","status":"PREPARING"}   (404 if the order does not exist, 422 for an unknown status)
```

### 8.14 Users and password reset

Account creation and password reset for the admin panel. **Every `/user/*` route needs the business key** in the `X-Business-Key` header, otherwise 401. Passwords are hashed with scrypt, `password_hash` is never returned.

| Method | Path | Body | Description |
|---|---|---|---|
| POST | `/user/login` | `username`\*, `password`\* | Sign in with a username and password. 200 with `{ id, username, role }`, 401 if credentials are invalid |
| POST | `/user/new_admin` | `username`\*, `password`\*, `email`\* | Create an `ADMIN`. 201 with the user, 409 if the username or email is taken. Requires `X-Business-Key` |
| POST | `/user/new_manager` | `username`\*, `password`\*, `email`\* | Create a `MANAGER`. Requires `X-Business-Key` |
| POST | `/user/reset_password_request` | `email`\* | Emails a 6 digit code to the account's email. Always 200, whether or not the account exists. 429 while the previous code is still valid |
| POST | `/user/reset_password` | `email`\*, `reset_code`\*, `new_password`\* | Sets the new password. 400 `Invalid or expired reset code` |

Rules: `username` 3 to 50 characters, `password` 8 to 128, `email` valid (stored lowercase). A reset code is valid for 5 minutes, single use, dies after 5 wrong guesses, and a new one cannot be requested until the 5 minutes are up. Codes live in server memory (`src/passwordResets.ts`), so a restart invalidates them and several server instances would need the request and the reset to hit the same one.

Setting the key on an existing business (new deployments get one from `POST /business`):

```sql
UPDATE public.business SET key_hash = encode(sha256('your-long-random-key'::bytea), 'hex');
```

```bash
curl -X POST localhost:8000/user/login -H 'Content-Type: application/json' -H 'X-Business-Key: <key>' \
  -d '{"username":"owner","password":"a-long-password"}'

curl -X POST localhost:8000/user/new_admin -H 'Content-Type: application/json' -H 'X-Business-Key: <key>' \
  -d '{"username":"owner","password":"a-long-password","email":"owner@example.com"}'

curl -X POST localhost:8000/user/reset_password_request -H 'Content-Type: application/json' -H 'X-Business-Key: <key>' \
  -d '{"email":"owner@example.com"}'

curl -X POST localhost:8000/user/reset_password -H 'Content-Type: application/json' -H 'X-Business-Key: <key>' \
  -d '{"email":"owner@example.com","reset_code":"123456","new_password":"another-long-password"}'
```

### 8.15 Payments

Stripe is the main provider, Shift4 is a fallback (503 `Shift4 is not configured` without `SHIFT4_SECRET_KEY`). `amount` is normalised to pence: a number is taken as pence, a string with a `.` as pounds (`"12.50"` is 1250). Failures return `{ "success": false, "error", "error_message" }`.

| Method | Path | Description |
|---|---|---|
| GET | `/payments/stripe/checkout-session?amount=&currency=` | Creates a PaymentIntent, returns `{ success, clientSecret }`. `/payments/stripe-checkout-session` is an alias |
| POST | `/payments/stripe/charge` | Body `amount`, `currency`, `paymentMethodId`. Creates and confirms a PaymentIntent |
| POST | `/payments/stripe/checkout-callback` | Body `stripeSessionId`. Verifies a Checkout session |
| GET | `/payments/checkout-session?amount=&currency=` | Shift4 signed checkout request, returns `{ success, clientSecret }` |
| POST | `/payments/charge` | Shift4. Body `amount`, `currency`, and `token` or `card` |
| POST | `/payments/checkout-callback` | Shift4. Body `shift4ChargeId`. Verifies a charge |

Success responses are `{ success, charge_id, amount, currency, status }` where `status` is `200` when paid and `402` when not.

## 10. Adding a new endpoint

1. **SQL** – add a static query to `src/queries.ts` and register it in `QUERIES` under the right verb.
2. **Validation** – add a zod schema to `src/schemas.ts` (and export the inferred type if you need it).
3. **Types** – add the row and response types to `src/types.ts`.
4. **Handler** – create `src/requestHandlers/<thing>.ts`: an `express.Router()`, routes at the top, handler functions below. Use `parseInput`, `dbGet/dbAll/dbRun`, and `transaction` for multi step writes. Throw `notFound` / `badRequest`, do not write `try/catch`.
5. **Mount it** – import the router in `src/server.ts` and `app.use(...)` it **before** `notFoundHandler`.
6. **Header** – start the file with a comment block listing its routes.
7. **Test** – add schema tests in `test/` and a block in `curl-tests.sh`.
8. Run `npm run typecheck && npm test`.

## 11. Security notes

- Branch-setting writes now require an active `ADMIN` or `MANAGER` user. The backend currently accepts `Authorization: Bearer <user-id>` where the user id comes from the `users` table; this is a stopgap until full Supabase Auth is wired in.
- Rate limiting: all clients share one budget, 5 requests per second and 300 per minute. Going over either blocks **everyone** with 429 for 60 seconds (`Retry-After` header). It is backed by Redis and shared across instances.
- The `/user/*` routes are guarded by the business key (`X-Business-Key`), which an admin panel running in a browser can read. Treat it as a shared secret for your own admin panel, not as user login.
- Password reset codes are emailed, kept in memory only (hash), expire after 5 minutes and are limited to 5 guesses.
- There is deliberately no HTTP route for sending email, an open one would let anyone send mail from your domain.
- The `/payments/*` routes are still public and take the amount from the client; the order total is not checked against the payment yet.
- SQL injection is not possible: all SQL is static and parameterised.
- Prices on orders are computed server side, the client cannot set them.
- The connection requires TLS (`ssl: "require"`).
- RLS is enabled on every table with no policies, so the Supabase REST API cannot read or write your data with the public key.
- `.env` holds the database password and Supabase secret key. It is git-ignored, keep it that way. If a secret was ever pasted somewhere public, rotate it in the Supabase dashboard.
- Internal error details are logged server side only, clients get a generic 500.

#### Ordering an offer

A bundle is one offer plus the product (and modifiers) chosen for each rule. Every rule of the offer must be answered once, with exactly `rule.quantity` products:

```json
{
  "branch_id": "<branchId>", "customer_name": "Jo",
  "offers": [
    { "offer_id": "<offerId>", "quantity": 2,
      "rules": [
        { "offer_rule_id": "<mainRuleId>", "items": [ { "product_id": "<productId>" } ] },
        { "offer_rule_id": "<drinkRuleId>", "items": [ { "product_id": "<productId>", "modifier_ids": ["<modifierId>"] } ] }
      ] }
  ]
}
```

The server checks that the offer is `active` and inside `starts_at` / `ends_at`, that each product belongs to its rule and is sold at the branch, and that the modifiers come from the rule's groups and respect each group's `required` / `min_selections` / `max_selections`. Otherwise 400.

Pricing (see `src/offerPricing.ts`), per bundle: list value = products (branch price) + modifiers.

| Type | Discount |
|---|---|
| `FIXED_PRICE` | products cost `price`, modifiers are charged on top |
| `PERCENTAGE` | `percentage` % of the list value |
| `FIXED_DISCOUNT` | `discount_amount`, never more than the list value |
| `BUY_X_GET_Y` | not a bundle (400 if sent as one), it applies automatically, see below |

Each bundle product is saved as an order item with `offer_id` / `offer_rule_id` (its `unit_price` is the list price). The discount is saved on `orders.discount` and as one `order_offers` row per bundle, and `total = subtotal - discount + delivery_fee`. The response includes `discount`.

#### BUY_X_GET_Y (automatic)

Nothing extra to send. Each rule of an active `BUY_X_GET_Y` offer means "buy `quantity` of the rule's products, get 1 more of them free". Matching normal `items` are counted together (modifiers ignored), and every full set earns one free unit of the cheapest matching product. E.g. a rule with `quantity` 2 and 2 matching items in the order adds 1 free unit. Free units are saved as order items named `<product> (free)` with price 0 and the `offer_id` / `offer_rule_id`, so `subtotal` and `total` do not change. Rules are evaluated independently.

## 12. Known limitations and roadmap

**Not implemented yet**

- Full authentication / roles. The branch-setting routes have a temporary id-based Bearer token gate, but the intended design is still Supabase Auth JWTs verified against `SUPABASE_JWKS_URL`, with admin / manager roles for write routes and per branch access for the KDS.
- Configurable `BUY_X_GET_Y` (the offer has no fields for X and Y, so Y is always 1 free unit of the same rule's products).
- Payment verification. A `payment` on an order is only recorded as `PENDING`, nothing confirms it with Stripe or another provider.
- A login endpoint for the `users` table (passwords can be set and reset, but nothing checks them yet).
- A `/deals` resource. The word "deal" in the old project maps to **offers** here.
- Delivery fee configuration. `delivery_fee` is currently supplied by the client, there is no per branch setting to calculate it.
- Status transition rules (e.g. blocking `COMPLETED` back to `PENDING`).
- Pagination on list endpoints.

**Behaviours to be aware of**

- Because updates use `COALESCE`, you **cannot set a nullable field back to `null`** through `PUT` (sending `null` means "unchanged"). Clearing e.g. a `description` needs an explicit design (such as a dedicated clear flag).
- `PUT /branches/:id/products/:productId` replaces the override as a whole: sending only `price_override` resets `active` to `null`.
- `GET /orders/:branchId` and `/orders/history/:branchId` return everything in one response, large branches will eventually need paging.

## 13. Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `SUPABASE_DB_URL or DATABASE_URL missing` on start | `.env` is not in the directory you ran `npm` from, or the variable is empty. |
| `/health` or any data route returns 500, `/` works | The database is not reachable. `/` does not touch the database. Check the server log for the real error (below). |
| `getaddrinfo ENOTFOUND <host>` | The host in the connection string is wrong or a placeholder (e.g. `aws-0-<region>`). Copy the exact string from Supabase. |
| `connect ECONNREFUSED 2a05:...:5432` (an IPv6 address) | The direct host `db.<ref>.supabase.co` resolved to IPv6 which your network cannot reach. Use the **Session pooler** connection string instead. |
| `password authentication failed for user "postgres"` (code `28P01`) | Wrong user or password for that host. On the **pooler** the user is `postgres.<project-ref>`, on the **direct** host it is `postgres`. Use the *database* password (reset it under Project Settings > Database), not the API keys. If the password contains `@ : / # ? &` it must be URL encoded (`@` becomes `%40`), and do not keep the square brackets from Supabase's `[YOUR-PASSWORD]` placeholder. |
| `relation "xyz" does not exist` | `schema.txt` has not been run on this database. |
| `400 Business already exists` | By design, one business per deployment. Use `PUT /business/:id`. |
| `409 Record is still referenced by other data` | You tried to delete something that orders (or other rows) still point to, e.g. a branch that has orders. |
| `422` with a list of fields | The request body failed validation, the message names each field. |
| Browser blocks requests (CORS) | Set `CORS_ORIGINS=*` for dev, or add the page's origin and restart. |
| `./curl-tests.sh: Permission denied` | `chmod +x curl-tests.sh`, or run `bash curl-tests.sh`. |
